Deploying lakebase-snapper

A step-by-step guide to deploy the app on Databricks and point it at the specific database — or databases — you want to monitor.

The app observes targets, stores into one repository DB, and serves the dashboard.

The one idea to hold onto

lakebase-snapper deals with two kinds of database, and keeping them straight is the whole game. A target is just a pair — (endpoint, dbname) — plus a friendly label. Targeting a specific database means adding the right pair to SEED_TARGETS.

Repository and target may share one Lakebase instance (simplest) or live on different instances. Each distinct instance the app touches needs the app's service principal registered there.

1 Deploy the app

Set your working values, then create the app and capture its service principal (SP).

# worked-example values — swap in your own
PROFILE=<PROFILE>
PROJECT=<LAKEBASE_PROJECT>
REPO_ENDPOINT=projects/$PROJECT/branches/production/endpoints/primary
REPO_DB=lakebase_snapper
APP=lakebase-snapper

databricks apps create "$APP" --description "Lakebase performance sampler" -p "$PROFILE"
SP=$(databricks apps get "$APP" -p "$PROFILE" -o json | jq -r '.service_principal_client_id')

Let the SP mint database tokens

Autoscaling Lakebase can't be attached as an app database resource, so the app mints OAuth tokens itself. Grant the SP CAN_USE on the project (additive — existing ACLs are preserved):

databricks api patch /api/2.0/permissions/database-projects/$PROJECT -p "$PROFILE" \
  --json "{\"access_control_list\":[{\"service_principal_name\":\"$SP\",\"permission_level\":\"CAN_USE\"}]}"

Create the repository & register the SP role

HOST=$(databricks postgres list-endpoints "${REPO_ENDPOINT%/endpoints/*}" -p "$PROFILE" -o json | jq -r '.[0].status.hosts.host')
TOKEN=$(databricks postgres generate-database-credential "$REPO_ENDPOINT" -p "$PROFILE" -o json | jq -r '.token')
EMAIL=$(databricks current-user me -p "$PROFILE" -o json | jq -r '.userName')

PGPASSWORD=$TOKEN psql "host=$HOST dbname=postgres user=$EMAIL sslmode=require" -c "CREATE DATABASE $REPO_DB;"

# register SP as a Postgres role + monitor grant (once per instance)
PGPASSWORD=$TOKEN psql "host=$HOST dbname=postgres user=$EMAIL sslmode=require" <<SQL
CREATE EXTENSION IF NOT EXISTS databricks_auth;
SELECT databricks_create_role('$SP','SERVICE_PRINCIPAL');
GRANT pg_monitor TO "$SP";
GRANT CONNECT ON DATABASE $REPO_DB TO "$SP";
SQL

# give the SP its own repository schema
PGPASSWORD=$TOKEN psql "host=$HOST dbname=$REPO_DB user=$EMAIL sslmode=require" <<SQL
GRANT "$SP" TO "$EMAIL";
CREATE SCHEMA IF NOT EXISTS snap AUTHORIZATION "$SP";
SQL

Configure, sync, deploy

Point app.yaml at the repository (PGUSER = the SP client-id), seed a target (next section), then:

WS="/Workspace/Users/$EMAIL/$APP"
databricks sync . "$WS" --exclude .venv --exclude __pycache__ --full -p "$PROFILE"
databricks apps deploy "$APP" --source-code-path "$WS" -p "$PROFILE"
Pin the SDK Set databricks-sdk>=0.132 in requirements.txt. The Apps base image ships an older SDK without the w.postgres API — leaving the default lets it linger and every token mint fails with a PoolTimeout at startup.

2 Target a specific database

Targets are a JSON array in SEED_TARGETS. Each entry names an endpoint and a database:

{ "label": "orders (prod)",
  "endpoint": "projects/<p>/branches/<b>/endpoints/<e>",
  "dbname": "orders" }
same instance

A database next to the repo

Nothing extra to grant — the SP already has pg_monitor here. Just name the database and redeploy:

[{"label":"orders","endpoint":"$REPO_ENDPOINT","dbname":"orders"},
 {"label":"billing","endpoint":"$REPO_ENDPOINT","dbname":"billing"}]
other instance

A database elsewhere

Two one-time grants on that project first, then add the target with its own endpoint:

# on the OTHER project/instance
databricks api patch .../database-projects/$OTHER -p $PROFILE --json '{...CAN_USE...}'
SELECT databricks_create_role('$SP','SERVICE_PRINCIPAL');
GRANT pg_monitor TO "$SP";

Or manage targets at runtime — no redeploy

The app exposes a small API (behind the app's sign-in, so call it from a browser session). Runtime targets persist in the repo; SEED_TARGETS is the durable way to declare them across redeploys.

CallDoes
GET /api/targetsList all targets
POST /api/targetsAdd {label, endpoint, dbname}
POST /api/targets/{id}/enabledEnable / disable (disabled targets let their endpoint sleep)
Expect this A target with no active sessions shows no ASH activity — that's correct, not a bug. Snapshots still accrue from cumulative pg_stat_statements counters, so the load profile and top-SQL-by-time views fill regardless.

Cost The collector polls continuously, so a monitored endpoint won't scale to zero while the app runs. Expected for a monitoring app — disable idle targets to let their endpoints sleep.

4 Verify & troubleshoot

Confirm the app is healthy and collecting:

databricks apps get "$APP" -p "$PROFILE" -o json | jq '.app_status'   # expect RUNNING
databricks apps logs "$APP" -p "$PROFILE-oauth" | tail -20            # scheduler started, snapshot N

Then open the app URL and hit /api/diag — a live self-test of the repository and every target, including whether the SP has pg_monitor vision. Empty charts almost always trace to a red line there.
